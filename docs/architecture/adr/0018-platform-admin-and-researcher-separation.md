# ADR-0018：平台管理员与研究用户的职责分离

- 状态：Accepted
- 日期：2026-07-26
- 决策者：Human
- 关联迭代：`docs/iterations/2026-08-r1-layer-contract-skeleton.md`

## 背景

引入 `Subject`（ADR-0012）后出现一个治理问题：**Subject 是全平台计算口径的来源**——改了它，之后所有结果的口径都变，而且不报错。同类问题也适用于 RulePack、数据源注册与基础数据：它们不是研究产物，而是研究的前提。

若任何有写权限的人都能修改这些内容，等于任何人都能悄悄改变全平台的计算口径，且改动的后果分散在此后所有结果中，难以归因。

ficant 是本地部署的开源平台，天然存在一个"建立者"角色——他配置这套系统、接入数据源、录入本机构信息。这与后续使用平台做研究的人是不同的职责。

方法论对此的一般原则是**靠遏制不靠枚举**：与其枚举所有不当修改的情形，不如从结构上限定谁能碰什么。

## 决策

**平台区分两类角色，按"数据是前提还是产物"划分职责。**

### 平台管理员（Platform Admin）

本地 ficant 的建立者。**拥有基础数据的写入权：**

- 数据源注册与凭据配置
- 可导入数据源与接口的**白名单**
- 基础数据（Instrument 主数据、日历、单位）
- 本机构数据（`Subject` 身份版本、`SubjectStateSnapshot`、`PositionSnapshot` 导入）
- RulePack 的引入与版本发布

### 研究用户（Researcher）

**默认只做研究：** 创建与运行 ResearchGraph、调用 AnalyticsService、创建因子定义与研究节点、发布研究产物。

研究过程中**可以引用和导入特定数据，但只能在管理员明确划定的数据源与接口白名单之内**。白名单之外的导入请求失败关闭，错误须指明该数据源未被授权，而非伪装成技术故障。

### 变更留痕

管理员对基础数据的每次变更必须记录**变更原因与依据文件引用**，规格与 `MarketRulePack` 的 `source_reference` 相同。

这使 `Subject` 在治理上靠近 RulePack，而不是靠近普通研究对象——**它们都是"外部事实的结构化"，不是"研究判断的产物"**。

### 与既有权限模型的关系

本 ADR 不替代 RBAC + ABAC，而是在其上确定**两个必须存在的角色与一条不可跨越的分界**：基础数据的写入权与研究权分离。更细的授权仍由 RBAC + ABAC 表达。

## 备选方案

1. **单一权限模型，靠 scope 粒度控制。** 否决：scope 是可授予的，缺少"这类数据在性质上不同"的表达；实践中会因为方便而把 `subject:write` 授予研究用户，分界随即消失。
2. **Subject 由研究用户自建，各自持有。** 否决：会产生多个互相矛盾的机构口径，且组合级结论无法比较。主体是平台级事实，不是个人偏好。
3. **不限制数据源导入，靠事后审计。** 否决：审计是滞后的，且导入未授权数据源的后果（数据泄漏、口径污染）不可撤销。遏制优于枚举。
4. **引入更多角色（审批者、审计员等）。** 否决：当前无真实需求。角色应由信号驱动新增，不预留插槽。

## 后果

- 首次部署需要一个明确的管理员初始化步骤，`MANUAL.md` 须补充该步骤。
- 研究用户在需要新数据源时必须走管理员，增加一次协调；这是有意的摩擦。
- 假想主体（如"如果我是保险"）的建立也归管理员——因为它同样是平台级口径。若实践中发现研究用户频繁需要临时假想主体做对比，本决定需重新评估。
- 开源单人部署场景下两个角色由同一人担任，但**权限仍分离**，以免单人部署养成的习惯带进多人部署。

## 验证与失效条件

- 验证：ACCEPTANCE `AC37`（研究用户导入白名单外数据源被拒绝，错误指明未被管理员授权而非伪装成技术故障）。角色分离条款已写入 SPEC v1.1 §5。
- 失效条件：若出现研究用户为绕过白名单而在 ficant 之外预处理数据再导入的普遍行为，说明白名单粒度过粗，需重新设计而非放宽。
