# ADR-0014：输出类型扩展为 PolicyArtifact；交付策略不执行策略，求值器共用

- 状态：Accepted
- 日期：2026-07-26
- 决策者：Human
- 关联迭代：`docs/iterations/2026-08-r1-layer-contract-skeleton.md`

## 背景

ficant 此前以"不做 OMS / EMS"划定与执行层的边界。业务侧研究给出的边界与此不同：

- 约四十个研究组件按频率重排后，**真正需要低延迟的只有 4 个，且全部在做市台**；其余三十余个是批处理或交易前查询。因此**边界应画在做市报价链路与其余部分之间**，不应画在"自研 vs 外采"或"信号 vs 订单"上。
- TCA、冲击成本模型、渠道选择、逆向选择检测、信息泄露测量属于日频或交易前查询的**建模与标定**，不是报单。以"不做 OMS"划界会把它们一并误伤，而这些恰是执行成本优化的全部内容——对 500 亿规模的组合，1bp 即 5000 万。

同时，做市定价能力的产出无法用现有输出类型表达。`SignalSet` 与 `TargetExposure` 都是**数值**；做市定价的产出是一个**函数**：给定券、库存、时刻 → 中间价 + 库存偏斜 + 价差。

第三个约束是可验证性。量化基础设施的经典事故是研究与实盘的实现分歧：回测一套代码、实盘另一套，逐渐漂移且无人察觉。若 ficant 交付策略描述、执行层照文档重新实现，**ficant 的血缘链在边界上断裂，下游全部不可验证**——这会抵消 ficant 存在的理由。

## 决策

### 一、新增输出类型 `PolicyArtifact`

ficant 的正式输出扩展为：`ResearchArtifact` / `SimulationResult` / `ReportArtifact` / `SignalSet` / `TargetExposure` / **`PolicyArtifact`**。

`PolicyArtifact` 装载**已标定的策略**：参数、适用券域、有效期、标定窗口、标定证据引用、求值器版本。它与 `SignalSet` 同级，同样要求完整血缘。

与 `CapabilityArtifact` 的区别：后者是**平台内**可复用的研究能力，前者是**交付给外部执行系统**的产物。

### 二、边界重述

**ficant 负责一切执行相关的建模与标定，不负责运行时调用。**

此表述取代旧的"不做 OMS / EMS"。据此：

- **属于 ficant：** 交易成本分析、冲击成本模型、渠道选择与拆单模型、逆向选择检测的标定、信息泄露测量、做市中间价模型。
- **不属于 ficant：** 订单生成与路由、订单生命周期管理、实时行情分发、策略的运行时调用、清算与结算。

### 三、求值器必须共用同一份实现

`PolicyArtifact` 必须与**求值器实现**一同交付。求值器是**可链接的库，不是服务**。

- 回测由它求值，实盘也由它求值；输入不同（快照 vs 实时流），**代码同一份**。
- 外部系统**不得**按文档重新实现策略。
- 判定方式：同一 `PolicyArtifact` 由 ficant 内部求值、与由外部程序调用同一求值器求值，对同一输入得到**逐位相同**的输出。

### 四、与实时行情系统的关系

实时行情处理属于执行层，不属于 ficant。但它承担双重角色，其中冷路径对 ficant 更重要：

统一交易决策函数所需的 X-Bond 盘口历史序列、货币中介报价流、自身完整询价日志（含未成交询价），**买不到，只能自己每天存**。因此实时管道的第一价值是为 ficant 生产不可再获得的历史，其正确性标准是**落地完整性**而非延迟；应按"冷路径优先"设计，与做市上线时间无关。

## 备选方案

1. **投研 / 信号 / 执行三个系统。** 否决：中间的"信号系统"没有自己的状态——它的输入要么来自实时行情（执行层已有），要么来自因子与定价库（ficant 已有）。独立成系统的唯一后果是重复订阅一份行情、重复实现一遍定价数学。**没有自己状态的东西不该是一个系统。**
2. **求值器做成服务，执行层通过 RPC 调用。** 否决：做市报价链路要求毫秒级，跨进程调用不可接受；且服务化并不能解决实现分歧问题，只是把它移到部署环节。
3. **只交付策略描述文档，由执行层实现。** 否决：血缘链在边界断裂，ficant 的证据体系失效。
4. **把做市报价链路也纳入 ficant。** 否决：为 4 个组件把整套架构做成低延迟的，代价极高且没必要；反过来把这 4 个塞进批处理体系，做市根本跑不起来。

## 后果

- ficant 的边界从"信号 vs 订单"移到"标定 vs 运行时调用"，覆盖范围实际扩大（纳入 TCA 与成本建模），但低延迟责任仍在外部。
- 求值器成为跨仓库的公共契约，需要版本化与兼容承诺——这是 ficant 第一处真正的**下游边界**（他人消费我），适用旧礼仪：版本化、废弃窗口、永不悄悄破坏。
- README §3.2 与 §3.3 的相关表述由 SPEC §2 的 B1 / B2 取代。

## 验证与失效条件

- 验证：ACCEPTANCE `AC24`（PolicyArtifact 可导出且含标定证据引用）、`AC25`（内外求值逐位相同）。
- 失效条件：若执行层出现 ficant 求值器无法满足的语言或运行时约束（例如必须以 FPGA 或特定嵌入式环境运行），"共用同一份实现"需改为"共用同一份规范 + 差分对拍"，且对拍必须是持续的而非一次性的。
